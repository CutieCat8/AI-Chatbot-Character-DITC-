# Gap Analysis — DITC CAT vs. สโคปจริง (2026-09-06)

เทียบทุกฟีเจอร์จาก `docs/scope/DITC_CAT_Project_Overview.pdf` + `docs/scope/ร่างขอบเขตงานคาแรคเตอร์ 45k.pdf`
กับโค้ดจริงในโปรเจกต์ ตรวจด้วยการอ่านโค้ด/เดินคำสั่งจริง ไม่ใช่เดาจากชื่อไฟล์หรือความจำ — ทุกแถวมีไฟล์
อ้างอิงที่ตรวจสอบได้ เวลาที่ประเมินเป็น **person-hours ของงานเดียว** (ไม่ได้หารด้วยจำนวนคนในทีม)

## สรุปสั้น ๆ ก่อน (คำตอบตรงคำถาม): เหลือ 13 วัน — **ไม่ทันตามสโคปที่เขียนไว้ในสัญญาจริง**

ของที่ทำได้ดีและใช้งานได้จริงแล้ว (RAG/KB, Admin Dashboard, Chat Demo, กลไก Voice Pipeline + Character
พื้นฐาน) เดโมได้แน่นอน แต่มี **2 รายการที่เป็นความเสี่ยงขนาดใหญ่ที่สุด** ซึ่งทำไม่ทันแบบตรงสโคป 100%
แน่ ๆ ในเวลาที่เหลือ:

1. **Wake-word "สวัสดีดิตซีแคท"** — ยังไม่มีเลยแม้แต่บรรทัดเดียว ของที่มีตอนนี้ (ปุ่มกด/VAD) ไม่ใช่สิ่ง
   เดียวกัน และสโคปยังบังคับให้ "ทดสอบความแม่นยำกับผู้ใช้จริงหลายคน" ด้วย — งานสร้าง wake-word
   ภาษาไทยที่รันในเบราว์เซอร์ได้ + ทดสอบจริงกับคนหลายคน ตามหลักคือ **3-5+ วันทำงานเต็ม** ขั้นต่ำ
2. **ไฟล์ต้นฉบับ Character + แอนิเมชันจริง** — ของที่มีตอนนี้เป็น SVG เขียนมือฝังใน `.tsx` โดยตรง
   ไม่ใช่ไฟล์ต้นฉบับที่ส่งมอบแยกได้ตามที่สัญญาระบุไว้ชัดเจน ถ้าจะทำงานอาร์ต/แอนิเมชันจริง (Rive/Lottie)
   ให้ได้มาตรฐานส่งมอบ ถือเป็นงานอีกก้อนใหญ่ที่ยังไม่เริ่มเลย

นอกจากนี้มี **จุดที่บล็อกไม่ใช่เพราะขาดเวลาทำงาน แต่เพราะยังไม่มีคำตอบจาก DITC** (ดูหัวข้อท้ายตาราง)
ถ้าไม่เริ่มคุยตั้งแต่วันนี้ บางจุดจะกลายเป็นตัวบล็อกส่งมอบทั้งระบบ ไม่ใช่แค่ฟีเจอร์เดียว

## จุดที่บล็อกด้วยการตัดสินใจ ไม่ใช่ด้วยเวลาทำงาน — ต้องเริ่มคุยกับ DITC วันนี้

รายการเหล่านี้ **ประเมินชั่วโมงไม่ได้จนกว่าจะมีคำตอบ** เพราะคำตอบที่ต่างกันทำให้งานที่ต้องทำต่างกันโดยสิ้นเชิง:

1. **เก็บประวัติการสนทนาแบบไหน** — TOR ข้อ 3.3 บอกว่า "ต้องรองรับการจัดเก็บประวัติการสนทนา"
   แต่ Overview บอกว่า "ไม่เก็บบทสนทนาแบบเต็ม เก็บเพียงหัวข้อสรุปและวันเวลา" (design เดิมของทีม
   ตาม `app/models/conversation.py` ก็ทำตามแนวทาง Overview) **สองเอกสารขัดกันเอง** ถ้า DITC ยืนยัน
   ว่าต้องการแบบ TOR (เก็บบทสนทนาเต็ม) จะกระทบ PDPA และต้องออกแบบใหม่ทั้งหมด
2. **สเปกเครื่องแม่ข่ายจริง** — ยังไม่รู้ว่าเครื่องที่ DITC จะให้ติดตั้งรัน Docker + e5-large (ต้องการ RAM
   พอสมควรสำหรับโมเดล embedding local) ไหว ถ้าไม่ไหวต้องเปลี่ยนมาใช้ embedding แบบ API (มีค่าใช้จ่าย
   เพิ่ม + ต้องรื้อ index ใหม่ทั้งหมด) **ควรถามและได้คำตอบภายในสัปดาห์นี้** ไม่งั้นอาจไปเจอวันติดตั้งจริง
   แล้วเครื่องรันไม่ได้ ซึ่งไม่มีเวลาแก้ทันแล้ว
3. **นโยบาย PDPA การเก็บเสียง** — สโคประบุว่าต้องยืนยันก่อนติดตั้งใช้งานจริง ยังไม่มีเอกสารนี้เลย
4. **ผู้รับผิดชอบค่า API รายเดือน** — Gemini Live/DeepSeek/e5-large (ตัวหลังฟรีเพราะรันเอง แต่ Gemini
   ยังใช้ free tier ที่มีเงื่อนไข "นำข้อมูลไปพัฒนาโมเดล" อยู่ — อาจต้องคุยเรื่องนี้คู่กันด้วย)

## ความเสี่ยงใหญ่ที่สุด 2 อย่าง (ขยายความ)

### 1. Wake-word

สัญญาระบุชัดว่าต้อง "ทดสอบความแม่นยำของ wake-word กับผู้ใช้จริงหลายคน...ตั้งแต่ช่วงต้นโครงการ" — ทีม
เคยพิจารณา Porcupine แล้วตัดออกเพราะไม่รองรับภาษาไทย (บันทึกไว้ใน `CLAUDE.md`) ตอนนี้ใช้ VAD
(ตรวจจับ "มีคนพูด" เฉย ๆ) หรือปุ่มกดแทนในทุกจุดของระบบ **ไม่มีที่ไหนตรวจจับคำว่า "สวัสดีดิตซีแคท"
โดยเฉพาะเลย** และการมีปุ่ม "เริ่มคุย" ที่ต้องแตะ ก็ขัดกับหลักการ "ไม่มีการสัมผัสหน้าจอเลยแม้แต่ครั้งเดียว"
ในเอกสาร Overview ตรง ๆ ด้วย (เหตุผลเชิงเทคนิค: เบราว์เซอร์บังคับต้องมี user gesture ก่อนถึงจะขอสิทธิ์
ไมค์ได้ — เป็นข้อจำกัดจริงของเว็บ ไม่ใช่เลือกทำแบบนี้เอง)

ทางเลือกที่ควรคุยกับ DITC (ไม่ใช่ตัดสินใจเอง ตามกติกาข้อ 5 ใน CLAUDE.md):
- ยอมรับปุ่มแตะ 1 ครั้งตอนเริ่มกะ/เริ่มวัน (ไม่ใช่ทุกครั้งที่มีคนมาใช้) แทนคำปลุกจริง
- ใช้ wake-word ภาษาอังกฤษสำเร็จรูป (เช่น Porcupine มีให้) แทนคำไทย ยอมเสียความเป็นธรรมชาติ
- ยอมรับว่า wake-word เป็น "เฟส 2" หลังส่งมอบหลัก แจ้ง DITC ตรง ๆ ว่าไม่ทันใน 40 วันนี้

### 2. ไฟล์ต้นฉบับ Character + แอนิเมชัน

ของที่ส่งมอบได้ตอนนี้คือ source code ที่มี SVG ฝังอยู่ในไฟล์ React — **ไม่ใช่ "ไฟล์ต้นฉบับ Character"**
ตามที่สัญญาระบุ (ซึ่งปกติหมายถึงไฟล์ที่แก้ไข/ใช้ต่อในโปรแกรมออกแบบได้ เช่น Rive/Lottie/AI/Figma)
ถ้าไม่มีใครในทีมมีสกิลออกแบบ+animate ตัวละคร นี่คืองานที่ต้องหาคนช่วยหรือประเมินใหม่ว่าจะส่งมอบ
ระดับไหน — ควรคุยกับ DITC ว่ายอมรับ "SVG คุณภาพ production พร้อมเอกสารกำกับ" แทน Rive เต็มรูปแบบ
ได้ไหม ถ้าเวลาไม่พอจริง ๆ

## สรุปตัวเลข (person-hours, ไม่รวมรายการที่บล็อกด้วยการตัดสินใจ)

| รายการ | ชม.ประเมิน |
|---|---|
| Re-scrape อัตโนมัติ | 3-4 |
| ดึงข้อมูลสดจากเว็บเมื่อไม่พบใน KB | 6-8 |
| ยืนยัน+ทดสอบตอบสองภาษา (output) | 2-4 |
| ตอบด้วยภาพประกอบ | 10-14 |
| ระบบฟีดแบค | 8-12 |
| Idle mode วนข่าว | 6-10 |
| แสดงอารมณ์ (แยกจาก state) | 6-10 |
| Auth guard เพิ่มความปลอดภัย admin API | 2-3 |
| คู่มือผู้ดูแลระบบ | 4-6 |
| เอกสารสถาปัตยกรรม | 3-5 |
| ทดสอบเสียงในสภาพแวดล้อมจริงหน้าบูธซ้ำ | 3-5 |
| **รวม (ไม่รวม wake-word และ character art)** | **~53-81 ชม.** |
| Wake-word (ถ้าจะทำให้ตรงสโคปจริง) | 24-40+ (ไม่รวมเวลาทดสอบกับผู้ใช้จริงหลายคน) |
| Character ไฟล์ต้นฉบับ+แอนิเมชันจริง | 16-32+ (ขึ้นกับทักษะทีม) |

53-81 ชม. สำหรับของที่เหลือ (ไม่รวม 2 ตัวใหญ่) ยังพอมีทางเป็นไปได้ใน 13 วันถ้าทำเต็มเวลา แต่ **บวก
wake-word + character art เข้าไปแล้วรวมกันง่าย ๆ เกิน 100 ชม.ของงานที่ยังไม่เริ่มเลยสักบรรทัด** ไม่นับ
เวลาทดสอบภาคสนามที่สัญญาบังคับไว้ (wake-word กับผู้ใช้จริงหลายคน, เสียงในที่มีเสียงรบกวนจริง) — ด้วย
เวลา 13 วันที่เหลือและมีค่าปรับรายวันผูกอยู่ **แนะนำให้เอาตารางนี้ไปคุยกับ DITC โดยเร็วที่สุดว่าจะตัด
อะไรออกจากขอบเขต หรือขอขยายเวลา** ก่อนที่จะเสียเวลาลงมือทำโดยไม่รู้ว่าอันไหนจะถูกตัดทิ้งทีหลัง
