# แผนทดสอบเสียงติ๊ก/ป็อบตอนแมวพูด (manual, ต้องทำบนอุปกรณ์จริง)

**สถานะบั๊ก:** ทดลองแก้แล้ว 3 รอบ ยังไม่ยืนยันด้วยหูจริง (ดู CLAUDE.md หัวข้อ "เสียงติ๊ก/ป็อบ
แทรกระหว่างแมวพูด") — ล่าสุด (2026-09-08 บ่าย, รอบที่ 3) ย้าย `CHUNK_RECOVERY_MARGIN_MS` จาก
`enqueueAudio` มาใส่ใน `computeChunkSchedule` ตรงๆ ครอบคลุมทั้ง `origin=flush` และ `origin=stream`
แล้ว (รอบก่อนหน้าครอบคลุมแค่ `flush` ซึ่งจาก diagnostic logging จริงพบว่าแทบไม่เกิดเลย — ตัวที่เกิด
จริงคือ `origin=stream`)

**⚠️ diagnostic logging ยังอยู่ในโค้ด (`[click-noise-debug]` ใน console):** เปิด DevTools (F12) →
Console เวลาทดสอบ จะเห็น log ทุกครั้งที่เกิด gap จริง พร้อมขนาด (ms) และ origin — ใช้เทียบก่อน-หลังได้
ว่าจำนวนครั้ง/ขนาดเปลี่ยนไปไหม ไม่ต้องเดาจากหูอย่างเดียว (ตัวเลข objective ช่วยตัดสินใจได้ชัดกว่า)

**ทำไมต้องทดสอบด้วยมือ ทำไม unit test อัตโนมัติไม่พอ:** เสียง artifact จริงเกิดจาก Web Audio API
เล่นเสียงออกลำโพงจริง — เทสอัตโนมัติที่มีอยู่แล้วใน
`frontend-character/src/hooks/useVoiceSocket.test.ts` เทสได้แค่ตรรกะเลข (คำนวณเวลาเริ่มเล่นก้อนเสียง
ถัดไปถูกไหม) ไม่ได้ยืนยันว่าหูมนุษย์ได้ยินเสียงติ๊ก/ป็อบจริงหรือเปล่า สองอย่างนี้ต้องทำคู่กัน อย่าใช้
ผลเทสอัตโนมัติผ่านมาสรุปว่า "แก้แล้ว"

## ก่อนเริ่ม

- [ ] รันตาม `HOW_TO_RUN.md` ให้ backend + frontend-character พร้อม (ดู CLAUDE.md: **ห้ามรัน
      Python/Docker/embedding บนแท็บเล็ต** — backend ต้องรันบนเครื่องแยกในวง LAN เดียวกัน)
- [ ] เปิด `frontend-character` ผ่านแท็บเล็ตจริง (Samsung Galaxy Tab S10 FE) ผ่าน Chrome เท่านั้น —
      **ห้ามสรุปผลจากเสียงที่ทดสอบบนแล็ปท็อป/เดสก์ท็อป** เพราะฮาร์ดแวร์ไมค์+ลำโพงต่างกัน และบั๊กนี้
      อาจสัมพันธ์กับ jitter ของอุปกรณ์เฉพาะเครื่อง
- [ ] เตรียมที่เงียบ (กันเสียงแวดล้อมปนกับเสียงติ๊กที่กำลังฟัง)
- [ ] ถ้าเป็นไปได้ อัดหน้าจอ+เสียงคู่ขนาน (เช่นด้วยมือถืออีกเครื่อง) ไว้เป็นหลักฐาน แนบไฟล์เสียง/วิดีโอ
      กับผลทดสอบทุกครั้ง — **ห้ามรายงานแค่ "ได้ยิน/ไม่ได้ยิน" ลอย ๆ โดยไม่มีหลักฐานแนบ**

## Test Case 1 — คำตอบสั้น (ประโยคเดียว)

**ขั้นตอน:** ถามคำถามที่คาดว่าคำตอบสั้น เช่น "DITC เปิดกี่โมง" กดเริ่มคุยแล้วพูดคำถาม รอฟังคำตอบ
จนจบประโยค

**เกณฑ์ผ่าน:** ไม่ได้ยินเสียงติ๊ก/ป็อบแทรกระหว่างแมวพูดเลยตลอดคำตอบ

**บันทึก:** จำนวนครั้งที่ได้ยิน + ประมาณตำแหน่งในประโยค (ต้น/กลาง/ท้าย) + ไฟล์เสียงที่อัดไว้

## Test Case 2 — คำตอบยาว (หลายประโยค)

**ขั้นตอน:** ถามคำถามที่คาดว่าคำตอบยาว เช่น "เล่าเกี่ยวกับ DITC ให้ฟังหน่อย" หรือ "มีบริการอะไรบ้าง"

**เกณฑ์ผ่าน:** เหมือน Test Case 1 — แต่คำตอบยาวมีก้อนเสียง (chunk) มากกว่า เป็นเคสที่ CLAUDE.md ตั้ง
ข้อสงสัยว่าเกิดถี่กว่า (jitter สะสมมากกว่าในเทิร์นเดียว)

**บันทึก:** เหมือน Test Case 1 — ให้สังเกตด้วยว่าความถี่ของเสียงติ๊กเพิ่มขึ้นตามความยาวคำตอบไหม
(ถ้าใช่ สนับสนุนสมมติฐาน "jitter สะสม" ใน CLAUDE.md)

## Test Case 3 — เทิร์นแรกของ session (ทันทีหลังกด "เริ่มคุย")

**ขั้นตอน:** กด "เริ่มคุย" ใหม่ (session ใหม่) แล้วถามคำถามแรกทันที ฟังตอนแมวเริ่มพูดคำแรก ๆ

**เกณฑ์ผ่าน:** ไม่มีเสียงติ๊กช่วงต้นของคำตอบแรก

**หมายเหตุ:** จุดนี้ตรงกับ batch-flush ตอน jitter buffer เต็ม (`JITTER_BUFFER_MS`=1500ms) — จาก
diagnostic logging จริง (2026-09-08) พบว่าจุดนี้ (`origin=flush`) แทบไม่เกิด gap เลยในทางปฏิบัติ
เก็บ log เทียบไว้ด้วยว่าเทสรอบนี้ตรงกับที่เจอไหม

## Test Case 4 — เทิร์นที่สองขึ้นไปในบทสนทนาต่อเนื่อง

**⚠️ เคสนี้สำคัญที่สุด:** จาก diagnostic logging จริงพบว่า gap ส่วนใหญ่เกิดที่นี่ (`origin=stream` —
schedule ทีละก้อนตอนรับผ่าน WS ระหว่างเทิร์น) ไม่ใช่ Test Case 3 — การแก้รอบที่ 3 (ย้าย margin เข้า
`computeChunkSchedule` ครอบทุก origin) ตั้งใจให้ครอบคลุมเคสนี้ด้วยแล้ว เปิด Console ดู
`[click-noise-debug]` เทียบจำนวนครั้ง/ขนาด gap ก่อน-หลังปรับ

**ขั้นตอน:** ถามต่อจากคำตอบก่อนหน้าอีก 2-3 รอบในเซสชันเดียวกัน (ไม่กดเริ่มคุยใหม่)

**เกณฑ์ผ่าน:** เหมือนเดิม — เทียบว่าความถี่/ความรุนแรงของเสียงติ๊กเปลี่ยนไปจากเทิร์นแรกไหม (เช่น
เครื่องเริ่มร้อน/หน่วยความจำสะสมทำให้ processing ช้าลงเรื่อย ๆ)

## Test Case 5 — ระหว่างมีโหลดอื่นในเครื่องพร้อมกัน (จำลองสภาพหน้าบูธจริง)

**ขั้นตอน:** เปิด Chrome tab อื่นเล่นอะไรเบา ๆ พร้อมกัน (หรือถ้ามีแอปอื่นที่บูธจะรันจริง) แล้วทำ
Test Case 1 ซ้ำ

**เกณฑ์ผ่าน:** เหมือนเดิม — เทียบว่าโหลดเครื่องเพิ่มทำให้เสียงติ๊กถี่ขึ้นไหม (สนับสนุน/หักล้าง
สมมติฐาน "เครื่องประมวลผลช้าทำให้ jitter buffer ตามไม่ทัน")
