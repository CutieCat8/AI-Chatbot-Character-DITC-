# Knowledge Base Audit — 2026-09-06

## แก้คำที่บอกผิดไปก่อนหน้านี้ (สำคัญ)

ในการทดสอบ voice pipeline รอบก่อน ผมสรุปว่า "ข้อมูลค่าเทอม SE ไม่มีในฐานความรู้" — **ผิด** ตรวจสอบ
เนื้อหาที่ scrape มาโดยตรงแล้วพบว่า **ข้อมูลค่าเทอมมีอยู่จริงสำหรับทั้ง 7 สาขา ทุกระดับปริญญา**
ปัญหาจริงคือ **retrieval ไม่ได้ดึง chunk ที่มีตัวเลขมาให้ LLM ใช้ตอบทุกครั้ง** (เจอทั้งสองแบบ:
บางครั้งดึงถูก บางครั้งดึงผิด แม้ถามคำถามเดียวกัน) รายละเอียดอยู่หัวข้อ "ปัญหา retrieval" ด้านล่าง —
เปลี่ยนแนวทางแก้จาก "ไปหาข้อมูลมาเพิ่ม" เป็น "แก้ retrieval/chunking" แทน

## 3. แก้ retrieval bug แล้ว วัดผลจริง 78% → 92% (2026-09-06 รอบสอง)

**วิเคราะห์ก่อนแก้: ทั้ง 5 ข้อ (ค่าเทอม SE ตรี/โท, DTM โท, เบอร์ติดต่อ, โดรน) ไม่ได้พังด้วยสาเหตุ
เดียวกัน — มี 2 กลุ่มสาเหตุที่ต่างกันชัดเจน:**

| กลุ่ม | ข้อที่เข้าข่าย | สาเหตุจริง (วัดตรง ๆ ด้วย `search()`/`keyword_search()`) |
|---|---|---|
| **A: bug ลำดับ merge** | เบอร์โทร/อีเมล, โดรน | vector search เจอ chunk ที่ถูกต้อง **อันดับ 1** (cosine distance ~0.13, เกือบสมบูรณ์แบบ) ทุกครั้ง — แต่โค้ดเดิมเอา `keyword_results` (ดัก substring กว้าง ๆ เช่น "SE" ที่ไปแมตช์ nav menu ทุกหน้า) ใส่ไว้**ก่อน** `vector_results` ในลิสต์รวม แล้วตัด `[:6]` ทำให้ noise ของ keyword เบียด vector ที่ถูกต้องตกไปทั้งที่มีอยู่ในผลลัพธ์ดิบจริง |
| **B: rank ต่ำเกิน top_k** | ค่าเทอม SE ตรี/โท, DTM โท | vector search เจอ chunk ที่ถูกต้องจริง แต่อยู่อันดับ 7-11 (จาก `top_k=4` เดิม) ไม่ใช่ปัญหาลำดับ merge — เป็นปัญหาความแม่นของอันดับ (ranking) ล้วน ๆ |

**วิธีแก้ (ไม่ต้อง reindex เลยสำหรับ 5 ข้อนี้ — เป็นแค่แก้โค้ด retrieval logic 2 จุด):**
1. สลับลำดับใน `run_retrieval()` (`routers/voice.py`) และ `ask()` (`routers/chat.py`): เอา
   `vector_results` ขึ้นก่อนเสมอ (ก่อนทั้ง `keyword_results` และ `expanded_results`) — แก้กลุ่ม A
2. เพิ่ม vector `top_k` จาก 4 → 12 **พร้อมเพิ่ม cap ผลลัพธ์สุดท้ายให้ >= top_k ด้วย** (`voice.py`
   cap 8→12, `chat.py` cap 6→12) — รอบแรกเพิ่ม top_k อย่างเดียวไม่พอ (cap ยังตัดทิ้งอยู่ดี) ต้อง
   เพิ่มคู่กันทั้งสองค่า — แก้กลุ่ม B

**ผลวัดจริง (รัน 36 คำถามชุดเดิมซ้ำผ่าน `/api/chat` จริง หลังแก้):**

| รอบ | ผ่าน | หมายเหตุ |
|---|---|---|
| ก่อนแก้ | 28/36 = 78% | baseline เดิม |
| หลังแก้ | **33/36 = 92%** | **ทั้ง 5 ข้อที่วิเคราะห์ไว้ผ่านหมด** (ยืนยันด้วย curl ตรง ๆ ทีละข้อ ไม่ใช่แค่เดา) |

**แต่เจอ 3 ข้อใหม่ที่พังแทน (ไม่ได้อยู่ใน 5 ข้อเดิม) — ต้องตัดสินใจต่อ ไม่ใช่แค่บั๊กเดียวกันซ้ำ:**

| คำถาม | rank จริงของ chunk ที่ถูกต้อง | ประเภทปัญหา |
|---|---|---|
| ค่าเทอม DG | 13 (เกิน top_k=12 มานิดเดียว) | กลุ่ม B ซ้ำ — เพิ่ม top_k อีกนิดน่าจะพอ |
| ค่าเทอม ANI | 28 | กลุ่ม B แต่ไกลเกินจะแก้ด้วย top_k อย่างเดียว (ต้องเพิ่มถึง 30 — prompt ใหญ่ขึ้นมาก) |
| CAMT มีปริญญาเอกไหม | **ไม่ติด top-12 เลยแม้แต่อันดับเดียว** — เอกสาร KIM-phd/DTM-phd จริงไม่ปรากฏเลย | ปัญหาใหม่: semantic gap — คำถามสั้น/นามธรรม ("มีปริญญาเอกไหม") embed ไม่ใกล้หน้าโปรแกรมเฉพาะเจาะจงพอ ไปใกล้หน้า "เกี่ยวกับเรา"/"ติดต่อเรา" แทน |

**สาเหตุร่วมที่ลึกกว่านั้น (ตรวจแล้ว): 180 จาก 414 chunks (43%) เป็นเนื้อหาซ้ำกันแบบตัวอักษรต่อ
ตัวอักษรข้ามเอกสารคนละหน้า** (ยืนยันจาก distance ที่เท่ากันเป๊ะระหว่าง chunk คนละ id) ต้นเหตุคือ nav
menu/sidebar ที่ scraper ดึงซ้ำทุกหน้า — **แต่ลองสุ่มดูตัวอย่างจริงแล้วพบว่าอันตราย**: บาง "ของซ้ำ"
เป็นเนื้อหาที่ถูกต้องและจำเป็นจริง ๆ ที่บังเอิญเหมือนกันข้ามหลักสูตร (เช่น "รอบที่ 2: Quota / รอบที่ 3:
Admission" — ข้อมูลรอบสมัครที่เหมือนกันทุกสาขาจริงเพราะเป็นปฏิทินกลางของมหาวิทยาลัย) **ถ้าลบ chunk
ซ้ำแบบไม่เลือกหน้า จะทำให้บางสาขาไม่มีข้อมูลรอบสมัครเหลืออยู่เลย** (สร้างบั๊กใหม่แทนที่จะแก้)

**ยังไม่ได้ลงมือลบ/แก้เนื้อหาในฐานข้อมูลเรื่องนี้ — รอตัดสินใจร่วมกับทีมก่อน** เพราะเป็นการแก้ไข
ข้อมูลที่ reverse ยากกว่าแก้โค้ด และมีความเสี่ยงจะสร้างบั๊กใหม่ตามที่เจอข้างต้น ทางเลือกที่คุยกันได้:
- แก้ที่ scraper ให้ไม่ดึง nav menu ซ้ำ **ตั้งแต่ scrape ครั้งหน้า** (ปลอดภัยสุด แต่ไม่ช่วยข้อมูลที่มีอยู่แล้ว)
- ลบเฉพาะ chunk ซ้ำที่เป็น "nav menu ล้วน ๆ" (คัดด้วยมือ/heuristic เข้มงวดกว่านี้ ไม่ใช่ "ซ้ำ 2+ เอกสาร" เฉย ๆ) แล้ว reindex เฉพาะเอกสารที่กระทบ (ไม่ต้อง re-embed ทั้งฐาน)
- ปล่อยไว้ก่อน (92% ถือว่าใช้งานได้จริงสำหรับเดโม) แล้วค่อยกลับมาแก้ทีหลังถ้ามีเวลา
