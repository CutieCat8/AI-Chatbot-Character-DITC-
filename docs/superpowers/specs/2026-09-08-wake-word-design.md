# Wake Word "สวัสดี ditc" — Design Spec

**สถานะ:** ยังไม่ทำ — spec นี้เขียนขึ้นก่อนเริ่มลงมือ (2026-09-08)
**เจ้าของงาน:** Por Diewtrakul

## บริบท / ทำไมต้องมี

CLAUDE.md ระบุว่าตู้จริง (Samsung Galaxy Tab S10 FE มีกระจกครอบ ไม่มี touchscreen) ต้องเริ่มบทสนทนา
ด้วยเสียงล้วนๆ ปัจจุบันมีแค่ปุ่ม "เริ่มคุย" (ไม่มี wake-word detector เลยทั้งโปรเจกต์) — งานนี้เพิ่ม
wake word ที่ตรวจจับวลี **"สวัสดี ditc"** แล้วเรียก `voice.connect()` อัตโนมัติแทนการกดปุ่ม

⚠️ **หมายเหตุสำคัญที่คุยกันไว้ก่อนเริ่ม:** TOR ฉบับสัญญาจริง (`docs/scope/ร่างขอบเขตงานคาแรคเตอร์
45k.pdf`) ไม่ได้บังคับ wake-word เลย — ข้อกำหนดนี้มาจาก `DITC_CAT_Project_Overview.pdf` (เอกสาร
ประกอบ) เท่านั้น ยังไม่ได้ยืนยันกับ DITC ว่า Overview ผูกพันเท่า TOR ไหม แต่เจ้าของงานตัดสินใจให้ทำ
ต่อแล้ว (ยืนยันในเซสชันที่บรีฟงานนี้)

## เป้าหมาย

1. ตรวจจับวลี "สวัสดี ditc" (รวมการออกเสียง "ดี-ไอ-ที-ซี" และ "ดิตซี/ดิทซี" ทั้งสองแบบเป็น positive)
   จากไมค์ที่ฟังต่อเนื่องตอนแมวอยู่ใน state idle/sleep
2. พอมั่นใจพอ (confidence สูงต่อเนื่องหลายเฟรม) ให้เรียก `voice.connect()` อัตโนมัติ — พฤติกรรมเหมือน
   ผู้ใช้กดปุ่ม "เริ่มคุย" เอง ทุกประการ
3. **เข้มงวดเรื่อง false-accept เป็นพิเศษ** — นี่คือ kiosk สาธารณะ คนเดินผ่านคุยกันตลอด ถ้าเด้งผิดบ่อย
   จะน่ารำคาญ + เปลืองค่า API + กิน Gemini session 15 นาที/ครั้งฟรีๆ **ยอมรับ false-negative สูงขึ้น
   ได้เพื่อแลกกับ false-accept ต่ำ** (ผู้ใช้ยืนยันชัดเจนแล้วในขั้นบรีฟ)

## นอกขอบเขต (YAGNI)

- ไม่ทดสอบ/ปรับจูนกับเสียงคนพูดจริงในเซสชันนี้ (โมเดลเทรนจาก TTS สังเคราะห์ล้วนๆ) — การันตีความแม่นบน
  เสียงจริงไม่ได้จนกว่าจะมีคนทดสอบบนแท็บเล็ตจริง (เฟส 3 นอกเซสชันนี้)
- ไม่ตัดปุ่ม "เริ่มคุย" ออก — wake-word เป็นทางเลือกเสริม ปุ่มยังอยู่เป็น fallback เสมอ
- ไม่ทำ noise-cancellation/AEC เพิ่มเติมสำหรับ wake-word listener (ใช้ audio path เดียวกับที่มีอยู่)
- ไม่ทำ UI แสดง state "waking" ใหม่ในรอบนี้ (CatFace มี render-state `waking` รออยู่แล้วจาก Figma แต่
  ยังไม่มีอะไรเรียกถึง — ถ้าจะต่อเข้าเป็นงานแยกทีหลัง ไม่ใช่ scope ของ spec นี้)

## สถาปัตยกรรม

### เฟส 1 — เทรนโมเดล (Python, รันในเซสชันนี้บนเครื่อง Mac)

```
backend/app/scripts/wake_word/
  generate_dataset.py   — สร้าง synthetic audio (positive + negative) ด้วย edge-tts + augmentation
  train.py              — เทรน CNN บน log-mel spectrogram, evaluate, export
  export_tfjs.py         — แปลงโมเดลเป็น TensorFlow.js format
```

**Positive samples:** วลี "สวัสดี ดี-ไอ-ที-ซี" และ "สวัสดี ดิตซี"/"สวัสดี ดิทซี" — สร้างด้วย edge-tts
หลายเสียงไทย (อย่างน้อยชาย 1 + หญิง 1 เสียง เช่น `th-TH-NiwatNeural`/`th-TH-PremwadeeNeural` ที่
โปรเจกต์เคยใช้มาก่อน) แปรความเร็ว (0.9x-1.15x) + pitch เล็กน้อย + ผสม background noise (เสียง
ห้องเรียน/ทางเดินสาธารณะ) ที่ระดับ SNR หลายระดับ

**Negative samples (เน้นหนักเพราะต้องเข้มงวด):**
- "สวัสดี" เดี่ยวๆ ไม่มี ditc ต่อ (คำนี้เจอบ่อยสุดในชีวิตจริง ต้องกันการเด้งผิดจากตรงนี้เป็นอันดับหนึ่ง)
- ประโยคไทยทั่วไปสุ่ม (คำถามตัวอย่างจาก `docs/knowledge-base-audit.md`/ระบบเดิม)
- เนื้อหา KB จริงของ DITC/CAMT อ่านออกเสียงเป็นประโยคยาว (โดเมนใกล้เคียงของจริงที่สุด)
- เสียงเงียบ + เสียงรบกวนพื้นหลังล้วนๆ (ไม่มีเสียงพูด)

**Feature extraction:** log-mel spectrogram (40 mel bins, หน้าต่าง 2.0s — เดิม spec เขียนไว้ ~1s ตอน
ร่างแรก ของจริงวัดจากคนพูดช้าสุดแล้วปรับเป็น 1.6s แล้วขยายเป็น 2.0s อีกครั้งวันที่ 2026-09-11 ตามคำขอ
ผู้ใช้ ดู handoff doc) — ต้องใช้ฟังก์ชันเดียวกัน
(ผลลัพธ์ตัวเลขตรงกัน) ทั้งฝั่งเทรน (Python) และฝั่ง inference (JS ใน browser) ไม่งั้นโมเดลจะทำงาน
ผิดเพี้ยนตอนไปรันจริง — จุดนี้เป็นความเสี่ยงทางเทคนิคที่ต้องเทสให้แน่ใจ (unit test เทียบ output ตัวเลข
ของ Python feature extractor กับ JS version ด้วย input เดียวกัน)

**โมเดล:** small CNN (2-3 conv layer + dense, แบบ Google Speech Commands `tiny_conv`/DS-CNN) เป้า
ขนาดไฟล์ <200KB หลัง export เป็น TensorFlow.js — เทรนด้วย Keras, บันทึก accuracy/precision/recall
บน held-out synthetic test set (แยกจาก train set ตาม voice/style ไม่ใช่แค่สุ่มแถว กัน data leak)

**เกณฑ์ผ่านเฟส 1 (ก่อนไปเฟส 2):** precision บน negative test set (โดยเฉพาะกลุ่ม "สวัสดี" เดี่ยวๆ)
ต้องสูง (เป้า false-accept rate ต่ำมาก ตามที่ผู้ใช้ยืนยัน "เข้มงวดมาก") — ถ้าเทรนแล้วยังไม่ผ่านเกณฑ์นี้
ต้อง**บอกผู้ใช้ตรงๆ ก่อนไปต่อเฟส 2** ไม่ใช่ส่งโมเดลที่ยังไม่ดีพอเข้า production เงียบๆ (ตาม CLAUDE.md
กติกาข้อ 1 — ห้ามอ้างว่าใช้ได้ถ้ายังไม่พิสูจน์)

### เฟส 2 — ต่อเข้าเบราว์เซอร์ (frontend-character)

```
frontend-character/
  public/models/wake-word/    — TF.js model files (จากเฟส 1)
  src/hooks/useWakeWord.ts    — hook ใหม่
```

`useWakeWord.ts`:
- เปิดสตรีมไมค์แยกต่างหาก (ไม่ผูกกับ `useVoiceSocket`'s `connect()`/`disconnect()` lifecycle) — เริ่ม
  ฟังตอน component mount, ทำงานเฉพาะตอน `catState` เป็น `idle`/`sleep` เท่านั้น (หยุดฟัง/ไม่ประมวลผล
  ตอน `wake` เพราะกำลังคุยกับ Gemini อยู่แล้ว ไม่ต้องกัน wake-word ซ้อน)
- รัน TF.js inference วน loop ทุก ~300-500ms บน sliding window ของเสียงล่าสุด
- **ต้องเจอ confidence สูงกว่า threshold ต่อเนื่องหลายเฟรมติดกัน** (ไม่ใช่เฟรมเดียว) ถึงจะยอมเรียก
  callback `onWakeWordDetected` — ค่า threshold/จำนวนเฟรมที่ต้องต่อเนื่องเป็นค่าคงที่ปรับได้ ตั้งต้น
  แบบเข้มงวด แล้วผ่อนตามผลทดสอบจริงเฟส 3
- `App.tsx` รับ `onWakeWordDetected` → เรียก `voice.connect()` เดียวกับที่ปุ่ม "เริ่มคุย" เรียก (ไม่มี
  code path แยก กันพฤติกรรมสองทางไม่ตรงกัน) **ข้อยกเว้นเดียวที่ตกลงเพิ่มทีหลัง (2026-09-11 ตามคำขอ
  ผู้ใช้โดยตรง):** wake-word ส่ง `voice.connect({ greetFirst: true })` ให้แมวทักทายก่อนเองแทนที่จะนั่ง
  รอผู้ใช้พูดเงียบๆ (เหตุผล: ผู้ใช้ไม่มีปุ่มให้กดยืนยันอีกทีหลัง wake-word ต่างจากปุ่ม "เริ่มคุย" ที่ตั้งใจ
  กดเพื่อพูดเองอยู่แล้ว) ปุ่ม "เริ่มคุย" ยังคงเรียก `voice.connect()` เฉยๆ ไม่มี flag นี้ พฤติกรรมเดิมทุก
  ประการ — ดู `docs/superpowers/specs/2026-09-08-wake-word-handoff.md` หัวข้อ "greet-first" สำหรับ
  รายละเอียด implementation (`useVoiceSocket.ts`, `routers/voice.py` ข้อความ WS ใหม่ `greet_first`)

**Half-duplex:** ต้องปิด wake-word listener ระหว่างที่ `useVoiceSocket` เชื่อมต่ออยู่ (catState !==
idle/sleep) กันชนกับไมค์ที่ half-duplex ใช้อยู่แล้ว (CLAUDE.md ห้ามรื้อ half-duplex)

## Error handling

- โหลดโมเดล TF.js ไม่สำเร็จ (เน็ตพัง/ไฟล์หาย) → log error, wake-word ปิดเงียบๆ, ปุ่ม "เริ่มคุย" ยังใช้
  ได้ปกติ (ไม่ทำให้แอปทั้งตัวพังเพราะ wake-word)
- ขอสิทธิ์ไมค์สำหรับ wake-word listener ไม่ได้ (ผู้ใช้ปฏิเสธ/เบราว์เซอร์บล็อก) → เหมือนข้อบน ปุ่มยังใช้
  ได้ปกติ

## การทดสอบ

- **เฟส 1:** unit test เทียบ feature extractor Python vs JS ให้ตัวเลขตรงกัน (input เดียวกัน) + วัด
  precision/recall บน held-out synthetic test set รายงานตัวเลขตรงๆ ก่อนไปเฟส 2
- **เฟส 2:** เทสได้แค่ว่า hook ต่อ pipeline ถูกต้อง (mock TF.js model + audio input จำลอง) — เทสไม่ได้
  ว่าตรวจจับเสียงจริงแม่นแค่ไหน (ข้อจำกัดเดียวกับที่เจอตอนเทสบั๊กเสียงติ๊ก — logic เทสได้ เสียงจริง
  เทสไม่ได้)
- **เฟส 3 (นอกเซสชันนี้ ต้องมีคนทดสอบจริง):** ทดสอบบนแท็บเล็ตจริงกับคนพูดหลายคน/หลายสำเนียง วัด
  false-accept/false-negative จริง ก่อนเปิดใช้งานจริงหน้าบูธ — ตรงกับที่สโคป (Overview) บังคับไว้ว่า
  ต้องทดสอบกับผู้ใช้จริงหลายคน

## ความเสี่ยงที่รู้อยู่แล้ว (บอกไว้ล่วงหน้า ไม่ใช่ข้ออ้างทีหลัง)

1. โมเดลเทรนจาก TTS สังเคราะห์ล้วนๆ ไม่มีเสียงคนจริงเลย — ความแม่นบนเสียงจริงยังไม่รู้จนกว่าจะเฟส 3
2. Feature extraction ต้องตรงกันเป๊ะระหว่าง Python (เทรน) กับ JS (inference จริง) ไม่งั้นโมเดลพังแบบ
   เงียบๆ (ตรวจจับไม่ได้เลย หรือเด้งมั่ว) — ความเสี่ยงทางเทคนิคที่ควบคุมได้ด้วยเทสเทียบตัวเลข
3. "เข้มงวดมาก" ตามที่เลือกไว้ แลกมาด้วย false-negative ที่อาจสูงขึ้น (ต้องพูดชัด/ลองซ้ำบางครั้ง) —
   ผู้ใช้รับทราบแล้ว
4. ยังไม่ยืนยันกับ DITC ว่า wake-word อยู่ในสโคปสัญญาจริงไหม (ดูหัวข้อบริบทด้านบน)
